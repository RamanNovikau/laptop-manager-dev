# Laptop Status Test

## Plan
1. Define laptop statuses, state and history types.
2. Implement a small status transition function with explicit allowed transitions.
3. Add the 14-day return rule using an injected `currentDate` argument.
4. Cover valid transitions, invalid transitions, terminal state, return window and history with Jest tests.
5. Run TypeScript compilation and the full test suite.

## Solution
The solution uses a single `changeLaptopStatus` function and a transition map. It returns a new laptop state instead of mutating the existing object, which makes the function easier to test and reason about.

The current date is passed to the function, so the business logic does not depend on the system clock. Every successful transition appends a history entry containing the previous status, new status and transition date.

When a laptop changes to `Sold`, the transition date is stored as `soldAt`. The return rule is inclusive: a return exactly 14 days after the sale is allowed. A return after 14 days is rejected.

No database, API, frontend or persistence layer is used because they are outside the task scope.

## What was unclear
The phrase "no later than 14 days after sale" does not explicitly define whether the 14th day itself is included. I interpreted it as inclusive, so exactly 14 days after the sale is still a valid return.

The task also does not specify where the sale date should be stored. I store it as `soldAt` in the laptop state when the laptop enters the `Sold` status. This makes the return rule deterministic and keeps the required business data with the state.

The task does not specify how the function should handle a `Sold` laptop without a sale date. The implementation rejects such a return with a clear error because the 14-day rule cannot be evaluated safely without the sale date.
